# Error standards (RFC 9457)

Hclapi adopts the standard Problem Details specification (RFC 9457) as its default error response format. When an error occurs, whether during request ingress, schema validation, or pipeline execution, the engine returns an `application/problem+json` payload containing structured metadata about the failure.

## Problem details format

Error payloads generated by Hclapi adhere to a structured schema:

```json
{
  "type": "https://github.com/ju4n97/hclapi/errors/invalid-json",
  "title": "Invalid Request Payload",
  "status": 400,
  "detail": "invalid JSON payload: invalid character '\"' after array element",
  "instance": "/api/v1/transform",
  "step": "ingress",
  "invalid_params": [
    {
      "name": "tags",
      "reason": "must be a valid JSON array"
    }
  ]
}
```

| Field                | Type     | Description                                                                               |
| :------------------- | :------- | :---------------------------------------------------------------------------------------- |
| **`type`**           | `string` | A URI reference that identifies the specific problem category.                            |
| **`title`**          | `string` | A short, human-readable summary of the problem type.                                      |
| **`status`**         | `int`    | The HTTP status code generated by the engine.                                             |
| **`detail`**         | `string` | A human-readable explanation specific to this occurrence.                                 |
| **`instance`**       | `string` | The URI path of the request that generated the error.                                     |
| **`step`**           | `string` | The identifier of the pipeline step where the failure occurred (when applicable).         |
| **`invalid_params`** | `list`   | Detailed parameter validation errors, including field names and specific failure reasons. |

## Ingress and transport errors

Transport-level errors are detected and handled before the pipeline begins execution.

### Malformed JSON payloads (400 Bad Request)

If an incoming request contains broken JSON syntax, the engine halts immediately and returns a 400 Bad Request response without executing downstream steps:

**Client request:**

```bash
curl -i -X POST http://localhost:8080/api/v1/sanitize \
  -H "Content-Type: application/json" \
  -d '{"tags": ["golang" "testing"]}'
```

**Engine response:**

```http
HTTP/1.1 400 Bad Request
Content-Type: application/problem+json

{
  "type": "https://github.com/ju4n97/hclapi/errors/bad-request",
  "title": "Invalid Request Payload",
  "status": 400,
  "detail": "invalid JSON payload: invalid character '\"' after array element",
  "instance": "/api/v1/sanitize"
}
```

## Declarative error handling in manifests

Business logic errors, authorization guards, and resource-not-found states are declared directly inside the pipeline using conditional `respond` blocks:

```hcl
endpoint "POST /api/v1/workspaces" {
  description = "Creates a new workspace with duplicate slug validation"

  pipeline {
    # 1. Validation guard for required fields
    respond {
      condition = ctx.request.body.name == null || ctx.request.body.name == ""
      status    = 422
      body = {
        type     = "https://github.com/ju4n97/hclapi/errors/validation-error"
        title    = "Unprocessable Entity"
        status   = 422
        detail   = "The 'name' field is required and cannot be empty."
        instance = ctx.request.path
      }
    }

    # 2. Database insertion attempt
    sql "insert_workspace" {
      connection = connection.postgres.main
      query      = <<-SQL
        INSERT INTO workspaces (name, slug)
        VALUES (@name, @slug)
        ON CONFLICT (slug) DO NOTHING
        RETURNING id, name, slug, created_at
      SQL
      args = {
        name = ctx.request.body.name
        slug = ctx.request.body.slug
      }
    }

    # 3. Conflict guard for duplicate slug
    respond {
      condition = steps.insert_workspace.rows_affected == 0
      status    = 409
      body = {
        type     = "https://github.com/ju4n97/hclapi/errors/conflict"
        title    = "Conflict"
        status   = 409
        detail   = "A workspace with the slug '${ctx.request.body.slug}' already exists."
        instance = ctx.request.path
      }
    }

    # 4. Successful creation response
    respond {
      status = 201
      body   = steps.insert_workspace.result
    }
  }
}
```

When a `condition` evaluates to `true`, the `respond` block writes the error payload, applies the HTTP status code, and halts further execution.

## Unhandled runtime failures (500 Internal Server Error)

When an unhandled exception occurs inside a step (such as a Starlark script division by zero or a database connection timeout), the engine catches the failure, logs the full trace internally, and returns a formatted 500 response:

```http
HTTP/1.1 500 Internal Server Error
Content-Type: application/problem+json

{
  "type": "https://github.com/ju4n97/hclapi/errors/pipeline-execution-failed",
  "title": "Pipeline Execution Error",
  "status": 500,
  "detail": "step \"compute_metrics\" starlark execution failed: runtime error: division by zero",
  "instance": "/api/v1/metrics"
}
```

## Custom error handler integration

When embedding Hclapi in a Go application, default error formatting can be overridden by configuring a custom `ErrorHandler` on `hclapi.Options`:

```go
package main

import (
 "encoding/json"
 "log"
 "net/http"

 "github.com/ju4n97/hclapi"
)

func main() {
  engine, err := hclapi.NewEngine(hclapi.Options{
    ManifestDir: "./config",
    // Custom error handler formats responses to match proprietary conventions
    ErrorHandler: func(w http.ResponseWriter, r *http.Request, problem hclapi.ProblemDetails) {
      w.Header().Set("Content-Type", "application/json")
      w.WriteHeader(problem.Status)

      _ = json.NewEncoder(w).Encode(map[string]any{
          "code":      problem.Status,
          "message":   problem.Detail,
          "path":      problem.Instance,
          "timestamp": r.Header.Get("X-Request-Timestamp"),
      })
    },
  })
  if err != nil {
    log.Fatalf("engine initialization failed: %v", err)
  }

  http.ListenAndServe(":8080", engine.Handler())
}
```
