# OpenAPI overview

`hclapi` statically analyzes your manifest Abstract Syntax Tree (AST) at boot time to compile a strict, 100% compliant **OpenAPI 3.1** specification.

You don't need to maintain separate YAML files, code annotations, or run external generators. The HCL manifest is the single source of truth for your API contract.

Additionally, `hclapi` mounts zero hidden routes. If an OpenAPI specification file or interactive reference portal is served by your application, it must be explicitly declared as an `endpoint` using an `openapi` handler.

## Derived elements

Because `hclapi` manifests are statically typed, the compiler maps every part of your manifest directly into the OpenAPI 3.1 document model:

| Manifest construct                   | OpenAPI 3.1 mapping                                            |
| :----------------------------------- | :------------------------------------------------------------- |
| `endpoint "POST /api/v1/users/{id}"` | `paths["/api/v1/users/{id}"]["post"]`                          |
| `description = "..."`                | `operation.description` and `operation.summary`                |
| `{id}` and `{filepath...}`           | `parameters` with `in: path`, `required: true`                 |
| `request.query` fields               | `parameters` with `in: query` (types, bounds, and defaults)    |
| `request.headers` fields             | `parameters` with `in: header` (casing and format constraints) |
| `request.body = schema.<name>`       | `requestBody.content["application/json"].schema`               |
| `respond { status = 200 }`           | `responses["200"]`                                             |
| `catch "23505" { status = 409 }`     | `responses["409"]` (Conflict)                                  |
| Schema validation engine             | `responses["422"]` (Unprocessable Entity)                      |
| `server.max_body_size` enforcement   | `responses["413"]` (Payload Too Large)                         |

:::info Catalog exclusion
Endpoints configured with an `openapi` handler (`"spec"`, `"ui"`, or `"template"`) are automatically excluded from the compiled OpenAPI operations catalog (`paths`) to prevent polluting client SDKs.
:::

## Explicit endpoint declaration

You control the exact path and renderer for your specifications and documentation portals:

```hcl
# Public interactive documentation portal using Scalar
endpoint "GET /docs" {
  description = "Public interactive API documentation."
  auth        = []

  openapi "ui" {
    renderer = "scalar"
  }
}

# Raw OpenAPI 3.1 JSON specification
endpoint "GET /openapi.json" {
  openapi "spec" {
    format = "json"
  }
}

# Raw OpenAPI 3.1 YAML specification
endpoint "GET /openapi.yaml" {
  openapi "spec" {
    format = "yaml"
  }
}

# Internal Swagger UI protected by Basic Auth
endpoint "GET /admin/swagger" {
  description = "Internal Swagger UI for engineering team."
  auth        = [auth.basic.admin]

  openapi "ui" {
    renderer = "swagger"
  }
}
```

## Static CLI export

You can export the compiled OpenAPI 3.1 document directly from your terminal or CI/CD pipeline without running an HTTP server:

```sh
# Export JSON to stdout
hclapi openapi -c ./api

# Export JSON to file
hclapi openapi -c ./api -o ./openapi.json --pretty

# Export YAML to stdout
hclapi openapi -c ./api --format=yaml

# Export YAML to file
hclapi openapi -c ./api --format=yaml -o ./openapi.yaml
```

The exported document can be fed directly into client SDK generators.
