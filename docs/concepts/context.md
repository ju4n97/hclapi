# The context topology

The execution context (`ctx`) is the state object passed through every pipeline. It encapsulates incoming HTTP request metadata, runtime telemetry, and the outputs generated by preceding pipeline steps.

## Context hierarchy

The context is structured into three primary namespaces:

```text
ctx
├── timestamp_epoch : int
├── request
│   ├── method      : string
│   ├── path        : map[string]string
│   ├── query       : map[string]string
│   ├── headers     : map[string]string
│   └── body        : any (dict / list / scalar)
└── steps
    └── <step_name>
        ├── result        : any
        └── rows_affected : int
```

## Request namespace (`ctx.request`)

The `ctx.request` namespace contains immutable data extracted from the incoming HTTP request during ingress.

| Field                 | Type                | Description                                                                    | Example                             |
| :-------------------- | :------------------ | :----------------------------------------------------------------------------- | :---------------------------------- |
| `ctx.request.method`  | `string`            | The uppercase HTTP verb.                                                       | `"GET"`, `"POST"`                   |
| `ctx.request.path`    | `map[string]string` | Extracted route path parameters matched against URI templates.                 | `ctx.request.path.id`               |
| `ctx.request.query`   | `map[string]string` | URL query string parameters.                                                   | `ctx.request.query.page`            |
| `ctx.request.headers` | `map[string]string` | Request headers with lowercased keys.                                          | `ctx.request.headers.authorization` |
| `ctx.request.body`    | `any`               | The unmarshaled JSON payload. Represented as a dictionary, list, or primitive. | `ctx.request.body.email`            |

### Path parameter resolution

Path variables declared in route patterns (e.g. `endpoint "GET /api/v1/accounts/{id}"`) are bound directly to `ctx.request.path.<name>`.

### Header canonicalization

All HTTP header keys are normalized to lowercase during ingress to ensure RFC-compliant, case-insensitive lookups across HCL expressions and Starlark scripts.

## Steps namespace (`ctx.steps`)

The `ctx.steps` namespace accumulates the outputs produced by completed pipeline steps. Each step writes its result under its declared block label.

```hcl
pipeline {
  sql "fetch_account" {
    # ...
  }

  starlark "format_profile" {
    # ...
  }
}
```

During execution, completed steps populate the context dynamically:

| Field                            | Type  | Description                                                    | Populated by                                 |
| :------------------------------- | :---- | :------------------------------------------------------------- | :------------------------------------------- |
| `ctx.steps.<name>.result`        | `any` | The computed output or returned record set from step `<name>`. | All steps (`sql`, `starlark`, `redis`, `go`) |
| `ctx.steps.<name>.rows_affected` | `int` | The number of rows modified or returned by the query.          | Database steps (`sql`)                       |

## Global runtime fields

| Field                 | Type  | Description                                                                   |
| :-------------------- | :---- | :---------------------------------------------------------------------------- |
| `ctx.timestamp_epoch` | `int` | Unix epoch timestamp in seconds recorded when the request entered the engine. |

## Accessing context data across environments

Context values are accessed through two distinct execution layers: HCL expression blocks and Starlark scripts.

| Target value        | HCL expression syntax               | Starlark script syntax                                             |
| :------------------ | :---------------------------------- | :----------------------------------------------------------------- |
| **Path parameter**  | `ctx.request.path.id`               | `ctx.request.path["id"]` or `ctx.request.path.get("id")`           |
| **Query parameter** | `ctx.request.query.filter`          | `ctx.request.query["filter"]` or `ctx.request.query.get("filter")` |
| **Header value**    | `ctx.request.headers.authorization` | `ctx.request.headers.get("authorization")`                         |
| **Body attribute**  | `ctx.request.body.name`             | `ctx.request.body["name"]` or `ctx.request.body.get("name")`       |
| **Step result**     | `steps.lookup.result.user_id`       | `ctx.steps.lookup["user_id"]` or `ctx.steps.lookup.get("user_id")` |
| **Timestamp**       | `ctx.timestamp_epoch`               | `ctx.timestamp_epoch`                                              |

In HCL expression blocks (such as `args`, `condition`, or `body`), `steps` is available at the root scope as a shorthand (`steps.<name>.result`). In Starlark scripts, all namespaces are nested under the primary `ctx` argument (`ctx.steps.<name>`).
